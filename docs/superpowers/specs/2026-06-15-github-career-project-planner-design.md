# GitHub Career Project Planner 设计规格

## 目标

创建一个名为 `github-career-project-planner` 的 Codex skill，用于根据用户目标岗位推荐适合学习的 GitHub 项目，并生成项目学习路线、可写入简历的项目描述和面试准备内容。

## 问题背景

准备求职的用户经常会问“有没有适合学习的 GitHub 项目”，但真正有价值的结果不只是仓库链接。用户需要的是：项目是否匹配目标岗位，是否适合当前水平，是否能在合理时间内学完，是否能做二次开发，以及是否能被可信地写进简历并在面试中讲清楚。

这个 skill 需要指导 Codex 联网搜索当前 GitHub 信息，避免只按 star 数推荐项目，并输出结构化的职业导向学习方案。

## 范围

第一版创建以下文件：

- `github-career-project-planner/SKILL.md`
- `github-career-project-planner/agents/openai.yaml`
- `tests/test_github_career_project_planner.py`

第一版不创建 GitHub API 客户端、爬虫、简历导出器、本地项目运行器或自动评分引擎。这些能力可以在后续使用中证明有必要时再迭代。

## 用户输入

skill 必须支持以下输入模式：

- 目标岗位，例如 Java 后端工程师、前端工程师、AI 应用开发、数据分析师、DevOps 工程师、全栈工程师或移动端开发。
- 可选的岗位 JD 或招聘描述。
- 可选的经验水平，例如初学者、学生、实习、校招、初级、中级或转行。
- 可选约束，例如偏好的编程语言、框架、项目难度、时间预算、输出语言，以及用户只想要简历项目描述还是完整学习路线。

如果关键信息缺失，Codex 应该在低风险场景下做合理默认假设；如果目标岗位或方向不明确，则提出一个简短问题确认。

低风险默认假设示例：

- 用户给了 JD 但没说经验水平：按 JD 中的年限、职位级别和技能要求推断目标水平。
- 用户说“Java 后端校招”但没给技术栈：默认围绕 Spring Boot、MySQL、Redis、消息队列、项目部署和基础工程化能力筛选。
- 用户只说“帮我包装这个仓库进简历”并提供仓库链接：不再搜索更多项目，直接评估该仓库并生成学习路线和简历描述。

高风险场景必须追问：

- 用户既没有目标岗位，也没有 JD 或仓库链接。
- 用户目标岗位互相冲突，例如同时要求“前端实习”和“资深后端架构”。
- 用户要求生成简历成果，但没有完成项目或计划完成的功能边界。

如果用户自述水平和 JD 要求冲突，例如用户说自己是初学者，但 JD 要求 5 年经验，Codex 应该优先相信用户自述水平，并把 JD 作为差距分析目标。输出中应明确说明“当前水平”和“目标岗位要求”的差距，而不是直接按 JD 高阶要求推荐过难项目。必要时可以追问用户是要“补差距路线”还是“短期简历包装”。

## 核心流程

使用 skill 时，Codex 必须：

1. 解析目标岗位、经验水平、约束条件和可选 JD。
2. 从用户请求或 JD 中提取岗位技能关键词。
3. 检查用户输入和 JD 是否存在水平、岗位或时间预算冲突，并按冲突处理规则处理。
4. 按精确搜索策略联网搜索与岗位和技术栈相关的当前 GitHub 仓库，避免只使用宽泛关键词。
5. 评估项目时优先使用 GitHub 仓库主页和官方文档等一手来源。
6. 根据岗位匹配度、学习价值、简历价值、维护信号、文档质量、可运行性、社区信号和二次开发空间评估仓库。
7. 避免只因为 star 多就推荐项目。
8. 解释每个项目为什么适合用户的目标岗位。
9. 为选中的项目生成学习路线。
10. 建议能形成个人差异化成果的二次开发任务，并按用户水平控制难度。
11. 默认生成中文简历项目描述，除非用户要求其他语言。
12. 为每个项目生成面试准备问题和讲解要点。

## GitHub 项目筛选规则

skill 必须要求 Codex 使用当前联网信息核实仓库状态，因为 GitHub 项目的活跃度、维护者、star、fork、是否归档和 issue 状态都会随时间变化。

如果当前环境不能联网，Codex 必须走降级路径：明确说明无法核实最新仓库状态，然后要求用户提供候选 GitHub 仓库链接、项目 README 内容或仓库摘要。只要用户提供仓库链接或足够的项目材料，skill 仍然应该完成项目评估、学习路线、二次开发建议、简历描述和面试准备，但必须标注“仓库活跃度未实时核实”。

## 搜索策略

Codex 不应该只搜索宽泛词，例如 `Java Backend Project`、`frontend project` 或 `AI project`。这类查询容易返回八股文仓库、学习笔记仓库、项目合集和过时示例。

搜索时应该组合以下信号：

- 岗位核心技术：例如 `Spring Boot`, `Redis`, `Kafka`, `React`, `Next.js`, `FastAPI`, `LangChain`, `Kubernetes`。
- 项目形态：例如 `ecommerce`, `blog`, `mall`, `chat`, `workflow`, `admin`, `dashboard`, `rag`, `microservices`, `observability`。
- 可运行信号：例如 `docker-compose`, `demo`, `deployment`, `production-ready`, `starter`, `example app`。
- 排除词：例如 `awesome`, `interview`, `notes`, `learning`, `tutorial-list`, `roadmap`, `八股`, `面试`, `学习笔记`。
- GitHub 限定：优先打开仓库主页，而不是只依赖第三方榜单、博客或项目合集。

推荐搜索表达式示例：

- Java 后端实习：`site:github.com spring boot redis docker-compose ecommerce OR mall`
- Java 后端微服务：`site:github.com spring cloud gateway nacos sentinel seata docker-compose`
- 前端工程师：`site:github.com next.js dashboard auth prisma docker`
- AI 应用开发：`site:github.com rag fastapi langchain vector database docker`
- DevOps：`site:github.com kubernetes prometheus grafana terraform example`

搜索结果处理规则：

- 优先选择完整应用、业务系统、可运行 demo、工程化样例和有清晰模块边界的仓库。
- 谨慎选择纯教程、学习笔记、面试题、awesome list、脚手架模板和只包含零散 demo 的仓库。
- 如果候选结果质量差，应该调整关键词并再次搜索，而不是硬凑推荐。
- 推荐前至少打开候选仓库页面核实项目定位、技术栈、README 和最近可见活动信号。

项目评估维度分为三档。

不可妥协维度：

- 是否匹配目标岗位和技术栈。
- 项目复杂度是否适合用户当前阶段，或是否能拆成适合当前阶段的学习路径。
- 是否具备简历包装价值。
- 是否能做原创性的二次开发，而不是只照抄 README。

重要维度：

- README 和启动文档是否清晰。
- 最近是否仍在维护，或即使维护较少也有明确学习价值。
- 架构和模块结构是否适合学习。
- 是否具备面试讨论价值。

加分维度：

- 可见 issue/PR 或社区维护信号较好，但不得编造精确统计。
- 有清晰的部署方式、测试用例或演示环境。
- 有具体证据显示社区或维护活动较多，例如最近提交、release、讨论或文档更新。
- 能覆盖岗位中的多个核心技能点。

Codex 应该明确标注那些虽然热门但不适合用户水平或简历目标的项目，并说明不推荐原因。

## 实时信息与幻觉边界

如果没有直接使用 GitHub REST API 或 GraphQL API，Codex 不得声称精确的 issue 解决率、PR 合并率、维护者响应时间、贡献者增长趋势或其他需要结构化统计的数据。

允许使用的表述：

- “从仓库页面可见信息看，最近有更新。”
- “README 较完整，包含启动或部署说明。”
- “issue/PR 页面需要进一步人工确认。”
- “当前无法可靠判断 issue 处理效率。”

禁止使用的表述：

- “该仓库 issue 解决率为 82%。”
- “维护者平均 3 天响应。”
- “PR 合并率很高。”
- “社区非常活跃。”除非给出具体可见证据，例如最近提交、release、讨论或文档更新。

如果只能通过网页浏览核实项目，输出中应把 `issue/PR 健康度` 降级为 `可见社区与维护信号`，并说明判断依据和不确定性。

## 输出契约

除非用户要求更窄的回答，skill 应该按以下结构输出。默认使用中文标题：

1. `岗位能力拆解`：目标岗位需要的技能、项目类型和能力关键词。
2. `GitHub 项目推荐`：仓库链接、技术栈、难度、推荐理由、风险说明和学习优先级；同时包含“不推荐及原因”子项，用于列出热门但不适合当前用户的项目。
3. `项目学习路线`：启动方式、代码阅读顺序、核心模块、实验任务和阶段性里程碑。学习路线的时间阶段必须根据用户时间预算自适应缩放，例如 2 周预算输出 2 周节奏，4 周预算输出 4 周节奏；如果用户没有给时间预算，默认给 3 到 4 周路线并明确假设。
4. `二次开发任务`：能让项目变成个人作品的具体改造任务，并按用户水平分级。初学者优先做小功能、UI、配置、接口和文档增强；校招或初级开发者优先做完整业务闭环、测试、部署和监控；中级用户可以做架构调整、性能优化、安全增强和可观测性建设。每个推荐项目至少覆盖两层改造方向，避免只给单点功能建议。
5. `简历项目描述`：可直接改写进简历的项目背景、技术栈、个人职责、亮点和可信量化结果。对于建议中的技术改造，必须给出符合行业常理的预期量化指标范围，并明确这是“预期目标”或“完成后可实测指标”，不能伪装成已完成结果。
6. `面试准备问题`：架构、取舍、性能、调试、部署、安全、扩展、技术选型与踩坑的问题。必须包含 `技术选型与踩坑` 类别，用于回答“为什么用这个技术”“不用它会怎样”“引入后有什么代价”“踩过哪些坑或可能踩哪些坑”。
7. `下一步行动计划`：未来 3 到 7 天的短期执行计划。

窄输出模式规则：

- 用户只要“项目推荐”：保留 `岗位能力拆解` 和 `GitHub 项目推荐`，省略完整学习路线和简历描述。
- 用户只要“学习路线”：保留 `GitHub 项目推荐`、`项目学习路线`、`二次开发任务` 和 `下一步行动计划`。
- 用户只要“简历描述”：保留必要的 `GitHub 项目推荐` 摘要和 `简历项目描述`，并补充少量 `面试准备问题` 以避免简历不可讲。
- 用户只要“面试准备”：保留项目摘要和 `面试准备问题`，按架构、技术难点、取舍和追问组织。
- 用户提供单个仓库链接：不输出多项目推荐表，改为输出该仓库的评估、学习路线、二次开发任务、简历描述和面试准备。

窄输出示例：

```text
用户：只帮我把这个 Spring Boot 商城项目写成简历项目，不用学习路线。
输出：保留项目摘要、可核实的技术栈、3 到 5 条简历 bullet、每条 bullet 对应的技术锚点和预期量化指标；补充 5 到 8 个面试追问，省略完整项目推荐表和周计划。
```

## 二次开发深度要求

`二次开发任务` 不应该只停留在“增加登录”“添加页面”“改 UI”这类泛化建议。Codex 应该根据岗位和项目类型输出分层改造方案：

- 业务闭环层：补齐真实业务流程，例如订单状态机、审批流、支付回调、库存扣减、权限审批、消息通知或数据导入导出。
- 工程质量层：增加单元测试、集成测试、API 文档、错误码规范、日志规范、配置分层、CI 检查和 Docker Compose 一键启动。
- 架构升级层：引入模块拆分、领域边界、缓存策略、异步任务、消息队列、限流熔断、分布式锁、读写分离或多租户设计。
- 性能与可靠性层：增加慢查询优化、缓存穿透/击穿/雪崩处理、压测脚本、指标监控、告警、链路追踪和故障降级。
- 安全与权限层：补充 RBAC、JWT 刷新机制、接口鉴权、数据权限、审计日志、敏感信息脱敏和基础安全防护。
- 部署与可观测性层：补充 Dockerfile、docker-compose、环境变量模板、健康检查、Prometheus/Grafana、OpenTelemetry 或日志采集。

二次开发建议必须包含：

- 任务目标：为什么这个改造对目标岗位有价值。
- 技术切入点：应该改哪些模块或新增哪些组件。
- 技术锚点：明确建议使用或强化哪些具体中间件、框架、协议、工具或组件，例如 Redis、Kafka、RabbitMQ、Elasticsearch、PostgreSQL、MySQL、Docker、Kubernetes、Prometheus、Grafana、OpenTelemetry、Nginx、JWT、OAuth2、RBAC、Spring Security、Celery、BullMQ、Prisma、LangChain、pgvector 或 Milvus。
- 可交付成果：最终能展示什么，例如接口、页面、部署地址、压测报告、架构图或 README。
- 简历表达：完成后可以如何写成一条可信 bullet，并给出合理量化基准或预期指标范围。
- 难度等级：初学者、校招/初级、中级。

每个推荐项目至少给出两个不同层级的改造方向。每个改造方向都应该能落到具体技术锚点和可交付成果上，避免只写“优化性能”“完善架构”“提升安全性”这类不可执行描述。

量化基准规则：

- 每个技术改造必须包含一个可验证指标，例如接口响应时间、吞吐量、缓存命中率、慢查询数量、构建时间、部署耗时、错误率、测试覆盖率、资源占用、任务处理延迟或人工操作耗时。
- 指标必须用合理范围表达，例如“目标将商品详情接口 P95 响应时间从 300-800ms 降到 80-200ms”，而不是无依据地写“提升 10 倍”。
- 如果没有压测或日志数据，必须写成“预期目标”或“完成后建议实测”，不得写成既成事实。
- 简历 bullet 应优先使用“设计并实现 X，目标/实测 Y，支撑 Z 场景”的结构。
- 对初学者项目，可以使用轻量指标，例如“接口数”“测试用例数”“部署步骤从 N 步减少到 M 步”“核心流程从手动配置改为一键启动”。

## 源码结构评估

对于优先级较高、准备深入学习或写进简历的项目，Codex 不应只看 README。应尽可能查看仓库目录结构、主要配置文件和关键源码入口，判断项目是否适合实战学习。

源码结构评估应关注：

- 是否存在清晰入口，例如 `main`、`app`、`server`、`src`、`cmd`、`packages` 或框架约定入口。
- 是否存在依赖和启动配置，例如 `package.json`、`pom.xml`、`build.gradle`、`requirements.txt`、`pyproject.toml`、`Dockerfile`、`docker-compose.yml`、`.env.example`。
- 是否存在清晰模块边界，例如 controller/service/repository、domain/application/infrastructure、frontend/backend、apps/packages 或 services。
- 是否存在测试、CI、部署或环境模板。
- 是否有明显风险，例如单文件巨型项目、缺少启动说明、依赖版本过旧、密钥写死、只有截图没有代码、只有 README 没有可运行实现。

如果无法查看源码结构，Codex 必须说明“未完成源码骨架核验”，并把该仓库的推荐置信度下调。

## 防卡壳学习路线

学习路线必须优先降低用户在项目跑通阶段的失败率。每个推荐项目的学习路线应包含：

- 最小启动路径：先用最少依赖跑通核心功能，优先选择 Docker Compose、官方 demo、示例配置或 mock 数据。
- 环境检查清单：列出语言版本、包管理器、数据库、缓存、中间件、环境变量和端口占用。
- 常见卡点预案：依赖安装失败、数据库初始化失败、环境变量缺失、端口冲突、版本不兼容、前后端跨域、容器启动失败。
- 降级路径：如果完整项目 1 到 2 小时内跑不通，先阅读模块结构、运行单元测试、启动最小服务、替换外部依赖为 mock，或换到同类备选项目。
- 验收信号：明确什么算“跑通”，例如首页可访问、登录成功、核心接口返回、任务队列消费成功、数据库有初始数据或 demo 流程闭环。
- 时间盒：为启动、阅读、二次开发和简历整理设置硬性时间上限，防止边缘问题吞掉整体进度。

时间盒建议：

- 项目筛选：单个候选仓库最多评估 10 到 15 分钟；超过时间仍无法判断质量则降级或放弃。
- 环境启动：完整启动最多投入 1 到 2 小时；超过后进入降级路径，不继续死磕依赖问题。
- 单个卡点：同一错误最多连续排查 30 到 45 分钟；超过后记录错误、搜索替代方案或切换到最小服务。
- 二次开发：每个改造任务必须能拆成 0.5 到 2 天的小任务；超过 2 天的任务需要继续拆分。
- 简历整理：每个项目至少预留 0.5 天整理 README、架构图、运行截图、压测或验证记录。

## Skill 元数据要求

`SKILL.md` frontmatter 只能包含：

- `name: github-career-project-planner`
- `description: ...`

`description` 必须覆盖：基于目标岗位的 GitHub 项目发现、学习路线、简历项目描述、面试准备、JD 分析和仓库评估。

`agents/openai.yaml` 必须包含与 skill 目标一致的展示元数据：

- `display_name`
- `short_description`
- `default_prompt`

第一版不需要其他可选界面字段。

实现 `agents/openai.yaml` 之前必须先查看现有 skill 的 `agents/openai.yaml` 示例或 `skill-creator` 的 `references/openai_yaml.md`，确认当前 Codex CLI 实际使用的字段名和格式。如果实际字段名与本规格中的 `display_name`、`short_description`、`default_prompt` 不一致，实现时应以本地规范为准，并同步更新测试断言。

## SKILL.md 结构要求

为降低长上下文下的注意力稀释，`SKILL.md` 必须使用严格的 Markdown 层级组织，并把绝对红线放在靠前位置。推荐结构如下：

```markdown
# GitHub Career Project Planner

## Critical Rules

## Inputs And Conflict Handling

## Search Strategy

## Repository Evaluation

## Output Contract

## Second-Development Guidance

## Source Structure Review

## Anti-Stall Learning Route

## Resume And Interview Guidance
```

`Critical Rules` 必须放在正文前部，并包含：

- 必须联网核实当前 GitHub 信息；无法联网时走降级路径。
- 不得只按 star 数推荐项目。
- 不得编造 issue/PR 解决率、PR 合并率、维护者响应时间或社区活跃度。
- 必须区分“推荐但有风险”和“明确不推荐”。
- 简历描述必须可信，不得把建议改造写成已完成成果。
- 如果无法查看源码结构，必须降低推荐置信度。

如果实现时使用 XML 标签，也可以用 `<critical_rules>` 和 `<output_contract>` 包裹关键规则；但第一版优先使用严格 Markdown，降低格式复杂度。

## 测试策略

实现必须使用 TDD：

1. 在创建 skill 文件之前先写测试。
2. 运行测试，并确认因为文件或必要内容不存在而失败。
3. 创建最小 skill 文件，让结构测试通过。
4. 添加或运行行为内容测试，验证 `SKILL.md` 包含必要指令。
5. 测试通过后再精简和润色文案。

测试套件必须验证：

- skill 目录存在。
- `SKILL.md` 存在。
- `SKILL.md` frontmatter 只有 `name` 和 `description`。
- skill 名称等于 `github-career-project-planner`。
- description 覆盖目标岗位、GitHub 项目、学习路线、简历项目、面试准备和 JD。
- 正文要求使用当前联网信息核实 GitHub 仓库。
- 正文包含无法联网时的降级路径。
- 正文包含精准搜索策略，并要求排除学习笔记、面试题、awesome list 和项目合集。
- 正文包含用户水平和 JD 要求冲突时的处理规则。
- 正文明确不能只按 star 数排序或推荐项目。
- 正文区分不可妥协维度、重要维度和加分维度。
- 正文禁止在没有 GitHub API 或明确证据时编造 issue/PR 精确指标。
- 正文包含要求的输出章节。
- 正文包含热门但不推荐项目的输出位置。
- 正文包含窄输出模式规则。
- 正文要求二次开发建议覆盖业务闭环、工程质量、架构升级、性能可靠性、安全权限或部署可观测性中的至少两个维度。
- 正文要求学习路线根据用户时间预算自适应缩放。
- 正文要求二次开发建议包含具体技术锚点。
- 正文要求每个技术改造包含合理量化基准或预期指标范围，并禁止把预期写成既成事实。
- 正文要求高优先级项目进行源码结构评估，无法评估时降低推荐置信度。
- 正文包含防卡壳学习路线，包括最小启动路径、环境检查、常见卡点、降级路径和验收信号。
- 正文包含启动、排错、筛选、二次开发和简历整理的时间盒建议。
- 正文要求面试准备包含技术选型与踩坑类别。
- `SKILL.md` 使用严格 Markdown 层级，并把 `Critical Rules` 放在正文前部。
- `agents/openai.yaml` 存在。
- `agents/openai.yaml` 的展示元数据与 skill 目标一致。

## 验收标准

工作完成条件：

- 所有测试在本地通过。
- skill 目录只包含第一版必要文件。
- 不加载额外引用文件也能理解 skill 的完整工作流。
- 工作流明确要求 Codex 浏览当前 GitHub 信息。
- 输出契约足够明确，另一个 Codex 实例可以稳定产出一致结构。
- 实现避免不必要的脚本、资产和引用文件。

## 风险与缓解

风险：Codex 推荐过时或已归档的项目。  
缓解：要求使用当前联网信息核实，并为每个仓库提供风险说明。

风险：Codex 使用宽泛关键词，搜到学习笔记、面试题、awesome list 或项目合集。  
缓解：要求使用技术栈、项目形态、可运行信号和排除词组合搜索，并优先打开 GitHub 仓库主页核实。

风险：Codex 推荐热门但太难或不适合写简历的项目。  
缓解：筛选标准必须包含阶段匹配度、学习价值、简历价值和二次开发空间。

风险：简历 bullet 夸大用户贡献。  
缓解：要求保持表述可信，区分“已完成内容”和“建议改造内容”。

风险：Codex 编造 issue/PR 健康度、维护响应速度或社区活跃度。  
缓解：没有 GitHub API 或明确网页证据时，只能描述可见维护信号和不确定性，不得生成精确统计。

风险：SKILL.md 内容较长，模型忽略中间约束。  
缓解：要求使用严格 Markdown 层级，并把 `Critical Rules` 放在正文前部，集中放置不可违反的规则。

风险：只看 README 导致高估项目质量。  
缓解：对高优先级项目要求查看源码目录、配置文件和关键入口；无法查看时降低推荐置信度。

风险：用户在项目启动阶段卡住并放弃。  
缓解：学习路线必须包含最小启动路径、环境检查清单、常见卡点预案、降级路径和跑通验收信号。

风险：用户把大量时间消耗在低价值 Bug 或低质量仓库上。  
缓解：为候选仓库评估、环境启动、单个卡点、二次开发任务和简历整理设置时间盒。

风险：简历描述只有“使用 Redis 提升性能”这类空泛表达。  
缓解：每个技术改造必须绑定可验证指标或合理预期范围，并区分预期目标和实测结果。

风险：面试官追问技术选型时用户无法防守。  
缓解：面试准备必须包含技术选型与踩坑类别，覆盖为什么选、替代方案、引入成本和可能问题。

风险：skill 变得过宽。  
缓解：第一版只聚焦指导流程和结构化输出，自动化脚本和导出器后续再做。

## 示例

示例输入：

```text
我想找适合 Java 后端实习生的 GitHub 项目，最好能写进简历。我会 Spring Boot 和 MySQL，Redis 只了解一点，有 4 周时间。
```

期望输出摘要：

- `岗位能力拆解`：指出 Java 后端实习重点是 Spring Boot、REST API、数据库设计、缓存基础、权限、部署和基础工程化。
- `GitHub 项目推荐`：推荐 2 到 4 个适合校招或实习阶段的项目，说明仓库链接、技术栈、难度和风险；同时列出 1 到 2 个热门但不推荐的项目，并说明例如“复杂度过高”“偏框架源码阅读”“不适合短期简历产出”。
- `项目学习路线`：按第 1 周跑通项目、第 2 周读核心业务、第 3 周完成二次开发、第 4 周部署和整理简历组织。
- `二次开发任务`：建议增加 Redis 缓存、接口鉴权、操作日志、Docker 部署或简单监控，并按难度分级；对能力更强的用户，可以加入订单状态机、Kafka 或 RabbitMQ 异步通知、JMeter 或 k6 压测报告、Prometheus 指标或 OpenTelemetry 链路追踪。
- `简历项目描述`：生成可信的中文 bullet，避免声称用户尚未完成的成果；例如“设计 Redis 缓存方案，目标将商品详情接口 P95 响应时间由 300-800ms 降至 80-200ms，并通过压测报告验证”。
- `面试准备问题`：覆盖接口设计、事务、缓存一致性、权限、部署、性能瓶颈、技术选型与踩坑。
- `下一步行动计划`：给出未来 3 到 7 天要完成的具体步骤。

## 自检

本规格没有占位内容。范围限定在一个 skill、一个 `openai.yaml` 和一个测试文件。工作流、输出契约、元数据要求、降级策略、冲突处理和 TDD 验收标准保持一致。
