# 高阶二次开发蓝图库

## 使用规则

每个推荐项目至少选择两层改造方向，避免只做 CRUD 包装。对初学者优先 Level 1 + 一个轻量 Level 2；对中级候选人优先 Level 2 + Level 3。每个任务必须包含适用场景、技术锚点、改造步骤、可交付物、验收问题、简历表达模板和预期量化指标范围。

## Level 1 业务闭环

- 适用场景：项目已能启动，但业务流程不完整，缺少可讲的真实闭环。
- 技术锚点：状态机、支付回调、权限审批、导入导出、通知、任务调度、审计日志。
- 改造步骤：补齐业务状态枚举；设计状态流转约束；增加失败重试和异常分支；补充接口测试；更新 README 流程图。
- 可交付物：状态流转图、核心接口、异常处理说明、测试截图或接口调用记录。
- 验收问题：哪些状态允许互相切换？重复回调如何保证幂等？异常分支如何补偿？
- 简历表达模板：围绕“业务闭环 + 异常处理 + 可验证结果”表达，不夸大性能收益。

## Level 2 架构与高并发

- 适用场景：项目已有核心查询、订单、消息或数据同步链路，需要形成技术深度。
- 技术锚点：Caffeine + Redis 多级缓存、Canal、RocketMQ、异步任务、限流熔断、分布式锁、延迟队列。
- 改造步骤：识别高频接口；定义缓存 key 和过期策略；增加本地缓存和远端缓存；处理一致性和回源；为异步链路增加重试与死信；压测前后对比。
- 可交付物：架构图、缓存策略说明、消息流转图、核心代码、压测报告、降级方案。
- 验收问题：多级缓存如何保证最终一致性？Canal 到 RocketMQ 链路积压如何排查？缓存击穿时如何保护数据库？
- 简历表达模板：设计并实现基于 Caffeine + Redis 的多级缓存架构，预期目标为核心查询接口 P95 延迟降低 30% 到 70%，完成后待实测。

## Level 3 治理与性能

- 适用场景：项目已具备基础业务和架构改造，需要体现工程治理、稳定性或性能意识。
- 技术锚点：动态线程池、DynamicTp、Prometheus、Grafana、OpenTelemetry、压测基准、灰度发布、降级开关。
- 改造步骤：定义核心指标；接入监控埋点；建立压测脚本；引入线程池参数配置；设置告警阈值；设计降级和回滚路径。
- 可交付物：监控面板截图、压测脚本、指标说明、线程池配置、故障演练记录、回滚方案。
- 验收问题：为什么使用动态线程池而不是固定线程池？线程池参数如何估算？指标异常时如何定位瓶颈？
- 简历表达模板：接入动态线程池与 Prometheus 指标监控，预期目标为压测场景下吞吐提升 20% 到 50%，并支持异常峰值下的快速降级。

## 防耗时预警

- 候选仓库评估：10-15 分钟/个，超过时间盒仍无法判断是否可运行、是否有源码骨架、是否适合二次开发时，降级或放弃。
- 环境启动超过 2 小时仍未跑通：停止深挖边缘报错，改走最小启动路径或换项目。
- 单个 Bug 超过 45 分钟没有定位方向：记录现象、日志和已尝试方案，切换到可交付模块。
- 二次开发任务：初学者控制在 0.5-2 天形成可展示闭环，超过预算时降级为 Level 1 业务闭环。
- 简历整理：至少预留 0.5 天补 README、架构图、指标来源和面试防守材料。
- 二次开发超过时间预算 30% 仍无可展示结果：降级为 Level 1 业务闭环，保留 Level 2/3 为后续计划。
